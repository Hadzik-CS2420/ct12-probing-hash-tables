🎯 Overview

CT 11 handled collisions by giving every bucket its own linked list. This activity does it without any linked lists at all. In open addressing every entry lives directly in the slot array, and a key that finds its slot taken simply walks forward until it finds an empty one. That is linear probing.

Storing everything in one contiguous array is faster to scan than chasing pointers around the heap — but it creates a problem chaining never had. Delete an entry from the middle of a probe run and you break the trail: every key that probed past that slot becomes unreachable. The fix is a tombstone, a slot marked DELETED rather than EMPTY, and getting tombstones right is most of this activity.

One file of implementation, 15 TODOs. Worth 30 points, and you can check your own score at any time.

📖 Learning Objectives

By completing this activity, you will be able to:

  • Explain open addressing and how it differs from separate chaining in both layout and cost
  • Implement linear probing for insert, search and remove, wrapping around the end of the array
  • Explain why a deleted slot must become a tombstone instead of being marked empty
  • Use first_deleted to reuse a tombstone on insert without creating a duplicate key
  • Explain primary clustering and why probing degrades sharply as the load factor rises
  • Rehash only the OCCUPIED entries on resize, so tombstones are cleared rather than carried over
  • Compare probing against chaining on cache behavior, memory overhead and worst-case cost

Part 1: The Constructor and Destructor

File: src/ProbingHashTable.cpp — sections 1 and 2

There is only one allocation in this whole table: the slot array itself. Each HashSlot already defaults to EMPTY, so unlike CT 11 you are not chasing uninitialized pointers — and the destructor is a single delete[], because there are no nodes to free.

That contrast is the point of the activity: one array, one allocation, no pointer chasing at lookup time.

Part 2: hash() — Already Written, Read It Anyway

File: src/ProbingHashTable.cpp — nothing to write here, 4 points already passing

This is the identical multiply-and-add function from CT 11, handed to you:

size_t hash_value = 0;
for (char c : key) {
    hash_value = hash_value * 31 + c;
}
return hash_value % capacity_;

Read it before moving on, because it explains the division of labour in the rest of the file. The hash function’s only job is to pick a starting index. What happens when that slot is taken is the collision strategy’s job — and in this table, that means stepping forward.

Checkpoint: both HashFunction tests already pass — 4 points, on a fresh clone.

Part 3: insert() — Probe Forward, and Mind the Tombstone

File: src/ProbingHashTable.cpp — section 4, worth 7 points

Four things happen in order, and the order matters:

  1. Resize first, if adding this entry would push the load factor past the threshold. Probing a nearly full table is where the cost explodes, so the check happens before the insert, not after.
  2. Hash the key to get the starting index.
  3. Declare int first_deleted = -1 to remember the first tombstone you walk past.
  4. Probe forward — wrapping with (index + 1) % capacity_ — until you find the key, a tombstone, or an EMPTY slot.
The trap: do not drop the entry into the first tombstone the moment you see one. The key might already be further along the probe run, and writing it early leaves two copies in the table. Keep probing to confirm the key is absent, then go back and use first_deleted if you saw one. See insert_tombstone_trap.png.

Checkpoint: all three ProbingInsert tests pass — 7 points, including HandlesCollisionsViaProbing.

Part 4: search() — What Stops the Probe

File: src/ProbingHashTable.cpp — section 5, worth 5 points

Hash, then walk forward comparing keys. The whole subtlety is in the stopping condition:

  • OCCUPIED with a matching key — found it.
  • DELETED — keep going. A tombstone means something used to be here, so the key you want may be further along.
  • EMPTY — stop, and return nullptr. Nothing was ever placed here, so nothing could have probed past it.

Treating DELETED like EMPTY is the single most common bug in this file, and it fails in a way that looks random: the keys that disappear are only the ones that happened to probe past a removed slot.

Checkpoint: both ProbingSearch tests pass — 5 points.

Part 5: remove() — Why a Tombstone Exists

File: src/ProbingHashTable.cpp — section 6, worth 6 + 3 points

Find the key the same way search does, then mark its slot DELETED and decrement size_. The slot keeps its contents; only the status changes.

Marking it EMPTY instead would be the obvious move and it is exactly wrong. An EMPTY slot tells every future search "stop, nothing is past here" — so any key that originally probed through this slot becomes unreachable, even though it is still sitting in the array. The tombstone is what keeps the trail intact.

Checkpoint: the three ProbingRemove tests and Tombstone.SearchProbesPastTombstone pass — 9 points. That last one is the test that proves the trail survived.

Part 6: resize() — Four Steps, and the Tombstones Go Away

File: src/ProbingHashTable.cpp — section 8, worth 5 points

In order:

  1. Save the old array in a local pointer.
  2. Allocate the new, larger array and point the member at it.
  3. Walk the old array and re-insert only the OCCUPIED entries.
  4. delete[] the old array.

Step 3 is where tombstones disappear: they are not OCCUPIED, so they are never carried across. A resize is the only thing that cleans them up, which is another reason probing tables resize earlier than chaining ones — tombstones lengthen probe runs just like real entries do, without holding any data.

Checkpoint: both ProbingResize tests pass — 5 points. TombstonesCleared checks step 3 specifically.

Part 7: print() and Seeing It Work

File: src/ProbingHashTable.cpp — section 9, not scored

Loop every slot from 0 to capacity_ - 1 and print its index, status and contents. No test scores it, and it is still the most useful thing in the file while you are debugging — a probe run, a cluster and a tombstone all become obvious the moment you can see the array laid out.

🔧 Common Problems

The build fails, or CMake does not configure

Check the bottom-left corner of VS Code reads Dev Container. If it does not, press Ctrl+Shift+P and run Dev Containers: Reopen in Container — with Docker Desktop running. Still stuck? Delete the build/ folder and run cmake -B build again.

Some keys vanish after a removal

search() is stopping on DELETED. A tombstone means "keep probing"; only EMPTY ends the run. This is why Tombstone.SearchProbesPastTombstone exists.

The same key ends up in the table twice

insert() wrote into the first tombstone it found instead of finishing the probe. Remember the index in first_deleted, confirm the key is not already further along, and only then reuse the slot.

The program hangs on insert or search

The probe loop never terminates because the index is not wrapping. Step with index = (index + 1) % capacity_, and make sure the loop can also exit on a full pass — otherwise a full table spins forever.

TombstonesCleared fails

The resize rehashed every slot rather than only the OCCUPIED ones, so the tombstones were carried into the new array. Skip anything that is not OCCUPIED.

Everything works until the table grows, then lookups miss

The entries were copied into the new array at their old indices. Indices come from hash(), which divides by capacity_ — a new capacity means every key has to be re-inserted, not moved.

Tests fail to build

The test file is not yours to edit — if it will not compile, a signature in ProbingHashTable.cpp no longer matches the header. Compare the method names, parameter types and const markers against include/ProbingHashTable.h.
